## The engineering problem

Memory is not full and the GPU is busy, yet a card with more peak compute barely helps. Compute units may be waiting for data.

> Keep this question in mind: Why can fewer FLOPs leave execution time unchanged?

**Arithmetic intensity · Memory-bound · Compute-bound**

> **In one sentence: Execution is limited by whichever is tighter: moving data or performing computation.**

Arithmetic intensity I is roughly floating-point operations divided by bytes transferred from the memory level under study. A simplified Roofline bound is min(peak compute, memory bandwidth×I). Registers, shared memory, cache, and HBM have different bandwidths; reuse changes actual HBM traffic.

For a teaching vector-add example, reading two FP32 values and writing one transfers about 12 bytes per addition, giving roughly 1/12 FLOP/byte before cache and other effects. Tiled matrix multiplication reuses data and often has higher intensity. Different operators need different remedies.

Small-batch autoregressive decode can reread large weights for very few tokens, making bandwidth more influential. Prefill has more parallel tokens and can amortize reads. Architecture, batching, context, communication, and hardware still determine the real bottleneck; this is not an absolute rule.

Check whether matrix shapes suit Tensor Cores, layout conversions are costly, or launch overhead dominates. Tiny tensors can be limited by CPU scheduling and launches rather than either component of the simple Roofline model.

**Upstream and downstream:** Larger batches can improve efficiency while increasing queueing and KV usage.

**LabBot in practice:** A small batch-one action head may be launch-bound. Try reducing fragmented operations or compilation/fusion before assuming complex CUDA code is required.
