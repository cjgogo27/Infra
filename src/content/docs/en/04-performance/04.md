## The engineering problem

A normalization pipeline launches several kernels and writes several intermediates. You want fusion, but testing only a conveniently divisible input is insufficient.

> Keep this question in mind: Why is one random-input comparison insufficient for a custom kernel?

**Kernel · Coalesced access · Fusion · Boundary mask**

> **In one sentence: Kernel programming schedules parallel work and data movement while preserving boundaries and numerics.**

CUDA involves grids, blocks, threads, warps, registers, and shared memory. Triton often expresses parallel computation over blocks of elements, leaving some mapping to the compiler. Memory access, layouts, and resource occupancy still matter.

For Triton vector addition, each program obtains an index range, masks indices beyond the array, loads a and b with that mask, adds them, and stores with a mask. Without boundary masking, a non-divisible final block can access out of bounds. Follow the official vector-add tutorial, then softmax and matrix multiplication.

Fusion reduces intermediate writes and launches—for example, combining scale, bias, and activation. Excessive fusion can increase register pressure, reduce concurrency, or prevent a mature library from selecting a better matrix kernel. More fusion is not always better.

Validate small/large sizes, non-divisible lengths, dtypes, extreme values, and NaN conventions. Changed floating-point order creates numerical differences; set appropriate absolute and relative tolerances. Mean error alone may hide rare severe errors.

**Triton the language** writes GPU kernels. **NVIDIA Triton Inference Server** deploys services. **TensorRT Plugins** add custom operations to TensorRT and must describe supported types, shapes, and serialization.

**LabBot in practice:** Start with a measured preprocessing or action-head hotspot. Retain correctness comparisons and performance across shapes before claiming kernel experience.
