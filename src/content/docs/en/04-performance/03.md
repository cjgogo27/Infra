## The engineering problem

Long sequences cause OOM. Calling empty_cache() does not fix it. Enabling compilation then makes the first inference unusually slow.

> Keep this question in mind: Why cannot empty_cache() free weights still used by the model?

**Activation checkpointing · Computation graph · Graph break · CUDA Graph**

> **In one sentence: Memory optimization changes when tensors exist; compilation changes how operations execute together.**

Training forward passes usually retain activations needed for backward. Activation checkpointing stores fewer intermediates and recomputes them during backward, trading compute for lower peak memory. Distinguish it from a saved training checkpoint. Random operations and mutable state inside recomputed regions require care.

PyTorch allocated memory describes active tensor allocations; reserved memory includes allocator-managed caching. empty_cache() frees unused cache, not live referenced tensors. Before blaming fragmentation, check for growing lists of outputs or loss tensors retaining computation graphs, then investigate changing shapes.

torch.compile captures and optimizes graphs. Data-dependent Python branches and changing shapes can cause graph breaks or recompilation. Report initial compilation separately and consider whether short jobs amortize it. CUDA Graph reduces repeated CPU submission overhead under constraints on addresses, shapes, and control flow; it is not the same mechanism as a compiler.

Begin with smaller microbatches, correct reference lifetimes, mixed precision, and recomputation; then consider state sharding or offload. CPU offload saves GPU memory but increases host-memory and transfer demand.

**Upstream and downstream:** Memory savings may permit larger batches but add compute or transfer costs. Measure useful throughput and quality.

**LabBot in practice:** A few fixed camera-resolution buckets may reduce recompilation. Changing resolution also changes visual information, so evaluate task success.
