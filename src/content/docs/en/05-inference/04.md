## The engineering problem

Offline benchmarks are fast, but online requests time out. Execution takes tens of milliseconds while queueing takes more than a second.

> Keep this question in mind: Why might the highest-throughput batch be unsuitable for serving?

**Continuous batching · Backpressure · Admission control**

> **In one sentence: Serving must bound waiting work so throughput gains do not become uncontrolled queues.**

Static batching waits for a batch to finish. Continuous batching lets completed sequences leave and new sequences enter, reducing waste from unequal output lengths. Prefill and decode also compete. Chunked prefill trades throughput, first-token latency, and gaps for already-generating requests.

Near saturation, queues can grow rapidly even when average execution time is unchanged. Limit concurrency, queued tokens, or cache budgets rather than relying on an infinite queue. Define timeouts, cancellation, and overload responses. Cancelled requests should release resources promptly.

A health check may only show that a process or basic endpoint is alive. Model readiness, actual executability, and remaining capacity need monitoring. Record queue time, execution time, KV use, failures, and client end-to-end latency.

State the load model. A fixed-concurrency closed-loop client reduces new arrivals when responses slow, potentially hiding overload. A configured-arrival-rate test exposes queues more readily but needs a bounded test size. Both are useful; their results are not interchangeable.

**Upstream and downstream:** GPU scheduling affects product SLOs, and retries can amplify overload. Budget retries and avoid redundant work.

**LabBot in practice:** Do not accumulate unlimited stale camera observations. Latest-observation policies and dropping obsolete work require a defined control contract; stale actions should not keep executing.
