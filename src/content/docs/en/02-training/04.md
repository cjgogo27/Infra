## The engineering problem

After a reboot you restore the weights, but the learning rate restarts and previously consumed data repeats.

> Keep this question in mind: Why is model.state_dict() alone not enough for resume support?

**Checkpoint · Resume · Atomic commit**

> **In one sentence: Resuming training requires process state, not just model weights.**

Inventory model, optimizer, scheduler, scaler, update count, random-number state, sampler position, configuration, and data version. Exact continuation also depends on worker prefetch, nondeterministic operations, and distributed execution. Loading a file is not proof of equivalent recovery.

Write to a temporary file or separate directory and mark completion only afterward. Atomic renaming may be available on the same filesystem; do not assume identical semantics for object storage or cross-filesystem moves. Distributed state may live on multiple ranks, so saving rank zero's local shard alone is insufficient.

Asynchronous saving can overlap computation, but must capture a consistent snapshot rather than write tensors while the optimizer changes them. Background saving consumes host RAM, network, and storage bandwidth. Wait for completion before exiting.

Test recovery: save at step N, continue K steps as a baseline, restore in a new process, and repeat K steps. Compare losses, parameters, and counters. A deterministic teaching example can demand exact or near agreement; define acceptable tolerances for real distributed jobs.

**Upstream and downstream:** Save frequency trades write costs against lost progress. If failures are uniformly distributed within a fixed save interval, expected lost progress is about half that interval; real failure distributions may differ.

**LabBot in practice:** Export image normalization, action units, dimensions, and coordinate-system versions alongside weights.
