## The engineering problem

You expect CT, SFT, and RL to differ only in their loss function, but the RL job spends most of its time waiting for generated samples.

> Keep this question in mind: Why can a framework that runs SFT quickly run RL slowly?

**Continued training (CT) · Supervised fine-tuning (SFT) · Reinforcement learning (RL)**

> **In one sentence: CT continues learning from data, SFT learns demonstrations, and RL also coordinates sampling, rewards, and updates.**

CT has team-specific meanings. Here it means continued training; confirm the meaning in an interview. Continued language pretraining often predicts the next token. SFT uses instructions and target responses, with explicit loss masks—for example, training on assistant responses while excluding padding.

A batch includes token IDs, attention masks, labels, and sometimes images and sample weights. Padding variable-length samples wastes computation. Packing increases the useful-token fraction but requires correct boundaries and attention isolation to avoid unrelated examples leaking information.

LLM RL generates responses, computes rewards and reference-policy or value-related quantities, then updates the policy. PPO commonly uses a critic; methods such as GRPO need not use a separate critic. One algorithm's components are not universal RL requirements. Sampling and updating have different memory and batching needs, and updated weights must reach the inference engine.

**Upstream and downstream:** Length distributions affect balance; reward services introduce waits; inconsistent tokenizers or templates invalidate comparisons.

**LabBot in practice:** Imitation learning can use offline observation-action pairs. Robot RL also requires environment stepping, resetting, and rewards. Track effective environment steps/s in addition to tokens/s.

Before acceleration, overfit one small batch to confirm samples, masks, and loss are aligned. Otherwise you may simply train the wrong objective faster.

### One explicit PPO teaching configuration

This example is **synchronous PPO in robot environments: an actor produces actions and a critic estimates state value**. It describes responsibilities and data flow. **It is not executable verl, Isaac Lab, or other framework configuration, and has no measured GPU results.** GPU_A/GPU_B are logical resource pools, not a promise that a model fits; small models can exercise the data flow on CPU.

~~~yaml
example: synchronous_robot_ppo
trainer_pool: GPU_A
rollout_pool: GPU_B
environments: 8
steps_per_environment: 32
samples_per_iteration: 256
minibatch_size: 64
update_epochs: 4
sampling_policy_version: v
publish_after_update: v_plus_1
~~~

Eight environments collect 32 steps each, giving 256 transitions, not 256 complete trajectories. Episodes can end and reset within the window, so boundaries must be recorded. This simplified iteration has 4×(256/64)=16 minibatch optimizer steps, then publishes one new sampling version. A policy version identifies a sampling/update protocol and need not equal the optimizer-step counter.

~~~text
publish actor v -> rollout workers + environments
                -> observations/actions/rewards/old_log_probs/boundary_flags
                -> bootstrap values + advantages + returns
                -> trainer: PPO actor loss + critic loss
                -> 4 update epochs -> checkpoint v+1
                -> publish actor v+1 -> workers acknowledge -> next rollout
~~~

The PPO ratio needs old_log_prob from sampling; do not overwrite it with probabilities from the updated policy. Environment rewards and the critic have different roles: the critic is not the reward function. This robot example has no frozen reference language model. LLM PPO with reference-policy KL also needs reference scoring and external reward scoring; this diagram is not a universal LLM RL recipe.

Check which step generates samples, which changes parameters, who retains old_log_prob, and when new weights can be sampled. Continue with [resource/failure responsibilities](/Infra/en/03-distributed/04/) and [environment boundaries and logs](/Infra/en/06-embodied/03/).
