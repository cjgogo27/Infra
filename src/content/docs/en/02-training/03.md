## The engineering problem

Every GPU step begins with a blank interval. A smaller model does not help, but synthetic data already on the GPU makes execution much faster.

> Keep this question in mind: Why are random GPU tensors a diagnostic rather than a production benchmark?

**DataLoader · Prefetch · Sharding · Data leakage**

> **In one sentence: Training must continuously deliver the next correct batch, not merely execute the model.**

Separate file reading, video decoding, augmentation, collation, and host-to-device transfer. Timing next(loader) alone can mislead: background prefetch hides work, while GPU synchronization can charge previous work to the current Python line.

Establish three baselines: fixed GPU tensors for compute; in-memory data plus transfer; real storage with full preprocessing. Compare them, then vary worker count, prefetch depth, pinned memory, and file layout one at a time. Excessive workers can exhaust RAM, shared memory, or file descriptors.

Small files increase metadata operations. Sharded storage improves sequential access but affects shuffling and retries. Compressed video saves space while increasing decoding and random-seek costs. Report hot-cache and cold-cache results separately.

Distributed sampling must prevent every rank from reading the full dataset. Advance shuffle state across epochs. Length bucketing reduces padding, but maintain appropriate randomness and monitor the sample distribution.

**Upstream and downstream:** Collection defines the data format. Do not discard timestamps or coordinate definitions just to increase speed. A busy GPU does not imply correct data.

**LabBot in practice:** Split training and validation by episode so adjacent frames do not leak across sets. Align images, joint states, and actions; determine whether a target means the current or next action. Visualize a complete sample before optimizing.
