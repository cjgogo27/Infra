## The engineering problem

Training disappears without a Python traceback. Another run leaves the GPU idle while the CPU is saturated. Model code alone cannot identify the failing layer.

> Keep this question in mind: Why can adding GPUs fail to help an idle GPU workload?

**Process · Thread · Host and device · Pinned memory**

> **In one sentence: Python submits work on the CPU and the GPU executes asynchronously, with memory and the operating system in between.**

Processes have separate address spaces; threads share process memory. A DataLoader often uses worker processes. Python, image decoders, and numerical libraries may also use different thread pools. More workers increase memory and scheduling costs.

GPU memory is separate from host RAM. Data generally travels from storage to RAM and then to the GPU. Pinned memory can support asynchronous transfers, but occupies host memory that cannot be freely paged out. non_blocking=True alone does not guarantee transfer/compute overlap: suitable memory, streams, and dependencies are also required.

On Linux, begin with:
~~~bash
nvidia-smi
nvidia-smi topo -m
ps -eo pid,ppid,stat,%cpu,%mem,cmd --sort=-%cpu
free -h
df -h
~~~
The first two inspect GPU processes and topology; the others inspect CPU, RAM, and disks. High GPU utilization means the device was busy within the sampling interval, not that peak compute was achieved.

The host OOM killer may terminate Python before it can report an exception. Inspect exit codes and scheduler records, then kernel logs when permitted. Host RAM exhaustion and GPU OOM are different failures. Use a scheduler or persistent session for remote jobs so an SSH disconnection is not confused with a training failure.

**Upstream and downstream:** CPU cores, NUMA placement, and storage throughput can limit GPU supply.

**LabBot in practice:** When camera decoding competes with inference for CPU time, inspect threads, queues, and decoding latency before adding GPUs.
