## The engineering problem

You want to demonstrate engineering ability, but “I changed some settings and it got faster” does not explain what you solved.

> Keep this question in mind: Can a project remain valuable when an optimization does not improve speed?

**Latency budget · Ablation · Regression validation**

> **In one sentence: A credible optimization project connects the problem, evidence, change, result, and limitations.**

Draw LabBot's timeline: exposure → decoding → state alignment → preprocessing → encoder → policy/action head → postprocessing → communication → execution. A teaching budget might use 100 ms total. This is neither a measured robot result nor a safety guarantee; the control task must define real requirements.

Do not sum stage means and call the result p95. Tail events can correlate and stages can overlap. Measure complete requests. Observation age at command dispatch better reflects closed-loop freshness than model execution alone.

A manageable preparation project measures a small single-GPU model, locates a real hotspot, changes one mechanism, preserves correctness on identical inputs, and reports warm-up, p50/p95, throughput, and peak memory. Transfer the method to an open VLA or vision model afterward. Without a GPU, complete CPU experiments and system design; do not describe them as GPU acceleration experience.

Keep versions, configuration, commands, raw results, analysis, and limitations in the repository. Faster execution with lower quality is still informative when stated honestly. An unsuccessful optimization can demonstrate diagnosis and useful negative results.

**Upstream and downstream:** Deployment changes need regression checks and rollback-compatible model/preprocessing versions. Interfaces should handle timeouts and reject stale actions.

**LabBot in practice:** Validate through offline replay, simulation, and controlled hardware tests. A model service does not replace controller limits, collision protection, or stop mechanisms.
