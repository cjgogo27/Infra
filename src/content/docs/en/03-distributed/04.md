## The engineering problem

Larger gradient buckets reduce collective calls, yet step time increases. Communication duration differs from communication exposed on the critical path.

> Keep this question in mind: Why can fewer collective calls fail to accelerate training?

**NCCL · Compute/communication overlap · Topology · Resource scheduling**

> **In one sentence: Optimize communication to reduce overall waiting, not simply an isolated timing number.**

All-reduce gives every participant the reduced result. All-gather collects shards. Reduce-scatter reduces then distributes pieces. All-to-all exchanges destination-specific blocks. Rank call order, counts, and dtypes must be compatible.

A ring all-reduce volume model gives roughly 2×(N−1)/N×M bytes per card for N cards and M bytes of data. Protocol, link, and latency costs remain; NCCL may choose other algorithms. This is not a direct predictor of measured time.

Small buckets start early but create many messages. Larger buckets improve individual transfers but may launch late. Ideally one bucket communicates while the next layer computes. Inspect dependencies and gaps in a timeline, as well as competition for bandwidth or compute.

Check live ranks and matching collectives, inspect topology, establish nccl-tests baselines on the same hardware and message sizes, then return to the model timeline. NCCL_DEBUG=INFO aids diagnosis; verbose logging need not stay enabled.

Multi-card scheduling must allocate useful groups of devices. The slowest heterogeneous GPU may limit synchronous training. CPU, RAM, shared memory, and network resources matter alongside GPU count.

**Upstream and downstream:** Bucket size and placement jointly determine overlap.

**LabBot in practice:** Separate gradient traffic from checkpoint uploads so storage-network contention is not mistaken for a gradient algorithm problem.

### Allocate resources and failure responsibility for the same PPO example

Use the [synchronous PPO configuration in Section 2.1](/Infra/en/02-training/01/). This is a teaching deployment diagram, not a scheduler job specification. Actual GPU capacity, CPU counts, and model size require separate measurement.

| Component | Owns | Waits for / produces | First failure response |
| --- | --- | --- | --- |
| Trainer, GPU_A | Actor, critic, optimizer, current sample batch | Waits for 256 valid transitions; produces weights and checkpoint | Preserve earliest error and step/version; discard incomplete update and follow recovery protocol |
| Rollout, GPU_B | Read-only sampling actor v | Waits for observations; produces actions, old_log_prob, version | Reject stale/mixed-version data; re-acknowledge weights after restart |
| Eight environments, CPU or chosen simulator device | Environment state, episode IDs, rewards, termination reasons | Wait for actions; return observations and rewards | Mark missing samples/reset reasons instead of silently fabricating complete trajectories |
| Coordinator | Iteration, member health, version acknowledgments, timeouts | Advances stages after required samples/acknowledgments | Bound waits and cancel the affected iteration rather than waiting forever |
| Checkpoint storage | Completion markers and recoverable state | Confirms complete saves | Distinguish partial files from recoverable snapshots and retain the previous complete state |

The teaching synchronization boundary is: finish sampling → finish updating → publish v+1 → all sampling workers acknowledge loading → begin the next rollout. Record weight bytes, transfer time, load time, and acknowledgment wait separately.

If the trainer itself uses DDP/FSDP, one failed rank affects its collective group. The coordinator should cancel and rebuild the affected group through the framework's recovery mechanism; starting one replacement process does not imply unfinished collectives can continue. This table describes responsibilities, not a universal recovery API.
