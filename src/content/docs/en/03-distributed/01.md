## The engineering problem

Single-card training works, but two cards are not twice as fast and validation examples appear twice. Understand what is replicated, partitioned, and synchronized.

> Keep this question in mind: Why cannot four-card DDP fit 40 GB of model state into each 16 GB GPU?

**Distributed data parallel (DDP) · Rank · Collective communication**

> **In one sentence: Cards process different data and synchronize gradients so their model copies update together.**

A typical GPU setup uses one process per card, with a model and optimizer in each process. LOCAL_RANK selects a GPU within a node; global rank identifies a process; world size is the process-group size. They are not interchangeable across nodes.

During backward, once all gradients in a bucket are ready, DDP starts its asynchronous reduction; remaining backward computation can overlap communication. Common DDP configurations produce gradients averaged across ranks. DDP does not partition input data automatically; use a distributed sampler or equivalent. Unequal valid-token counts also require correct loss weighting.

DDP usually does not reduce model state per card. More data-parallel copies cannot fix a model that does not fit one card. During accumulation, no_sync() can avoid redundant communication for early microbatches. Both forward and backward belong inside the context; the last microbatch must synchronize.

Ranks must execute compatible collective sequences. Early exits, unequal batch counts, or different control-flow branches can leave peers waiting. Investigate the earliest failing rank before increasing an NCCL timeout.

**Upstream and downstream:** Global batch changes convergence; slow cards and links determine waits. Distributed validation samplers may pad with repeated examples, so count correctly.

**LabBot in practice:** Different video lengths create different rank workloads. Compare per-rank step times, not just rank zero's mean.

### Two buckets: communication starts during backward

This is a sequence diagram, not a measured GPU trace or a fixed millisecond scale. Assume backward produces bucket A before bucket B, and all ranks issue collectives in the same order.

~~~text
time ->       t0             t1             t2           t3
backward      [compute A]    [compute B]
bucket A                    [all-reduce A-------]
bucket B                                   [all-reduce B---]
optimizer                                                [step]
~~~

Bucket A can reduce at t1 while B is still being computed. Required gradient synchronization must complete before the optimizer uses those gradients; the diagram does not permit reading unfinished reductions. Actual overlap depends on dependencies, streams, hardware, and configuration. One large bucket may delay all communication until t2.

Why cannot four-card DDP fit 40 GB of model state into each 16 GB GPU?
