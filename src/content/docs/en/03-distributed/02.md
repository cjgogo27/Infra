## The engineering problem

Parameters, gradients, and Adam state dominate GPU memory. More cards should help hold the model, not merely run more copies.

> Keep this question in mind: Why can FSDP still run out of memory?

**Fully sharded data parallel (FSDP) · ZeRO · All-gather · Reduce-scatter**

> **In one sentence: Keep state sharded between operations and exchange parameters when needed, trading communication for memory.**

ZeRO can be understood through progressively sharding optimizer state, gradients, and parameters. Fully sharded FSDP likewise uses partitioned state and on-demand gathering, but APIs and implementation details are not identical.

For one layer, imagine gathering parameters, executing forward, then releasing or resharding according to policy. Backward gathers needed parameters again, and reduce-scatter aggregates and distributes gradient shards. Retention and prefetch depend on implementation and configuration. Lower persistent memory does not imply peak memory falls exactly with card count.

Wrapping granularity matters. One large unit may gather a huge parameter set at once. Transformer-block units make peak control and overlap easier; overly fine units create many small communications.

FSDP2 uses composable fully_shard and DTensor mechanisms. Do not mix old FSDP1 wrapper examples indiscriminately. Start with the official tutorial matching your installed version and record that version.

**Upstream and downstream:** Sharding changes checkpoints and export. Gathering full weights may need extra host RAM. Slow links can make memory savings cost step time.

**LabBot in practice:** Shard the large language backbone without unnecessarily fragmenting a small action head. First determine whether peaks come from persistent state or visual activations; recomputation may better address the latter.
