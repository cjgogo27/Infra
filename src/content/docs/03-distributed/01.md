## 现场问题

单卡正确，两卡没快两倍，验证数据还重复了一遍。先搞清哪些东西被复制、分配和同步。

> 带着问题读：为什么四卡 DDP 不能让 40 GB 模型状态装进每张 16 GB 卡？

**分布式数据并行（DDP）、进程编号（Rank）、集合通信（Collective）**

> **一句话听懂：各卡处理不同数据，同步梯度后让模型副本共同更新。**

典型配置是一进程一卡，每个进程有模型和优化器。LOCAL_RANK 选择节点内 GPU；全局 rank 标识进程；world size 是进程组规模。多机时不能把它们混用。

局部前向反向之后，梯度桶就绪便启动归约。常见 DDP 配置得到跨 rank 平均梯度，但不会自动分配输入数据，还需分布式采样器。有效 token 数差异大时也需正确加权 loss。

DDP 通常不减少每卡模型状态。模型单卡放不下，加数据并行副本也放不下。梯度累积可用 no_sync() 避免前几个 microbatch 的多余通信，前向反向都要在对应上下文内，最后一次仍需同步。

各 rank 必须以相容顺序执行集合通信。某卡提前退出、样本数不一致或走了不同分支，都可能让其它卡一直等待。NCCL timeout 发生后先找最早异常，不先调大超时。

**上下游影响：** 全局 batch 改变收敛，网络和慢卡决定等待；分布式验证采样可能补齐重复项，统计时要正确计数。

**LabBot 落地：** 不同视频长度让各 rank 负载不同，比较每卡 step time，不能只看 rank 0 平均值。
