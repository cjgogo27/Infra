## 怎样使用

下面三组情景均为教学设例，不是生产故障记录。先只读第一条信息，口头回答“还需要什么证据”，再展开后续信息。面试看的是定位路径与验证能力，不是一次猜中答案。

## 情景一：GPU利用率低

初始信息：训练GPU利用率约30%，同事建议把DataLoader worker翻倍。

先回答：你会询问哪些环境、输入和计时条件？什么证据才能支持worker调整？

<details>
<summary>追加证据与追问</summary>

完整数据路径每步120ms，替换为常驻GPU的同shape张量后为40ms；真实路径在前向前有明显等待。以上数字仅为本题设定。

追问：能否宣布磁盘是瓶颈？下一步只做哪一个对照？

参考思路：先确认两种输入的计算和shape可比，怀疑上游供给，但不能只凭差值区分读取、解码、增强或传输。增加“内存样本＋相同预处理/传输”的对照，并按阶段标记。worker增多还可能带来RAM与调度开销。最终以不带profiler的端到端吞吐和质量验证。

</details>

## 情景二：长序列OOM

初始信息：相同模型短序列能训练，长序列第一步OOM，empty_cache没有效果。

先回答：要收集哪些显存、shape和执行阶段的信息？为什么不是立即开启更多数据并行？

<details>
<summary>追加证据与追问</summary>

权重与优化器配置没变；峰值出现在反向附近；减小microbatch可以运行。数字不必假定，现场应查allocated/reserved、活跃tensor与峰值时间。

追问：先选重算、FSDP还是清缓存？怎样证明选择正确？

参考思路：这些证据让激活压力成为优先假设，但还需测量，不足以排除工作区或引用保留。先用小microbatch建立基线，再单独评估激活重算的显存/时间代价；若持久状态占主导，再考虑分片。DDP复制模型状态，不自动减少每卡状态。用固定有效batch和正确loss归一化比较，并检查质量。

</details>

## 情景三：NCCL timeout

初始信息：双卡任务中rank0报告通信超时，rank1日志暂时没有查看。

先回答：第一步看什么？会立即调大timeout吗？

<details>
<summary>追加证据与追问</summary>

rank1在更早时刻遇到样本shape错误并退出；rank0随后等待集合通信。

追问：为何看到NCCL错误不等于网络故障？修复后怎样验收？

参考思路：时间顺序说明timeout可能是次生症状。保留各rank最早异常与输入摘要，修复样本契约及异常退出传播，再检查各rank批次数和集合调用顺序。复跑含坏样本的受控测试，确认明确报错且所有进程退出；正常样本完成训练、参数一致。若之后仍超时，才继续检查拓扑、通信基线和网络，不能用本题结论排除所有通信问题。

</details>

## 代码题一：这测到的是GPU计算时间吗？

假设model与x已经在CUDA上：

~~~python
start = time.perf_counter()
y = model(x)
elapsed = time.perf_counter() - start
print(elapsed)
~~~

指出异步问题，写出测量边界，并说明想测“设备片段”还是“完整调用”。

<details>
<summary>答案要点</summary>

代码可能主要测提交时间。完整同步调用墙钟测量需先预热，区间前后同步，反复记录；输入准备若不属于测量目标则放在区间外。设备片段可用正确记录并同步的CUDA Events。不要在每个算子后同步后再声称测到了原本的流水线重叠。可参照实验A，但其串行调用不是在线服务最大吞吐。

</details>

## 代码题二：本意是每批独立更新，哪里错了？

~~~python
for x, target in loader:
    loss = loss_fn(model(x), target)
    loss.backward()
    optimizer.step()
~~~

<details>
<summary>答案与追问</summary>

缺少每次独立更新前的optimizer.zero_grad，梯度默认累加。增加清梯度并不把权重清零。

若本意改成梯度累积，就不能简单每批清空：先定义累积窗口和有效项权重，窗口开始清梯度，多个microbatch backward，窗口结束step；正确处理不足额尾窗口。用 [实验E](/Infra/labs/05-accumulation/) 检查全量与加权累积的一致性，而不是只背除以累积次数。

</details>

## 评分标准

每组情景与每道代码题各0–3分，共15分：

| 分数 | 表现 |
| --- | --- |
| 0 | 无法解释现象，或跳过正确性直接报优化收益 |
| 1 | 能列相关术语/常见原因，但没有优先级和证据 |
| 2 | 能提出合理假设，索取关键证据并设计一个隔离对照 |
| 3 | 在2分基础上说明替代解释、正确性门槛、验收与局限 |

自测分数只用于发现薄弱项，不预测面试通过率。三分钟回答可以短，但必须说清下一步如何验证。

## 三分钟项目叙述与交付

“在【硬件、版本、模型与输入】下，我观察到【问题】。通过【日志/trace/对照】定位【瓶颈】。只改变【机制】后，在【正确性门槛】下得到【实际结果与波动】。代价是【成本】，局限是【未覆盖条件】。”

报告保留：环境与命令、基线、原始记录、正确性、单项改动、结果、负结果和局限。没有测量写“未测”。阅读了解、实际运行、独立优化是不同层级；合成CPU实验不应写成大规模训练或真机加速经历。
