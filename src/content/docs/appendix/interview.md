## 先用自己的话回答

| 问题 | 回答应包含的要点 |
| --- | --- |
| GPU 利用率低怎么查？ | 时间线、数据供给、CPU、拷贝、同步，先隔离基线 |
| batch 增大必然更好吗？ | 吞吐、显存、延迟和收敛的权衡 |
| DDP 与 FSDP 差在哪里？ | 副本 vs 状态分片，通信时机与显存峰值 |
| TP=4 是否让有效 batch 乘四？ | 不会，它共同处理一份样本 |
| OOM 怎么处理？ | 先定位活跃状态、激活或工作区，再选择手段 |
| empty_cache 能救一切 OOM 吗？ | 不能释放仍被引用的活跃 tensor |
| 如何测 CUDA 时间？ | 异步执行、边界同步、Events、预热、测量范围 |
| 如何判断通信瓶颈？ | 同 rank 配置、拓扑基线、时间线、暴露通信 |
| 模型权重为何不够恢复训练？ | 优化器、调度器、RNG、采样进度与版本 |
| 量化后为何不提速？ | 内核、反量化、硬件支持、实际瓶颈 |
| Prefill 与 decode 有何差别？ | 并行 prompt 处理与迭代生成，缓存与负载 |
| VLA 优化有何特殊性？ | 视觉、动作头、时间戳、观测年龄、动作语义 |
| 如何组织 RL 训练？ | rollout、奖励/环境、更新、权重同步和滞后 |
| 如何证明优化可信？ | 同条件基线、正确性门槛、原始数据与局限 |

## 三分钟项目叙述

“我在【硬件、版本、模型、输入分布】下观察到【具体问题】。通过【日志/trace/对照】定位到【瓶颈】。我只改变【一项机制】，与原基线比较，得到【实测指标、样本数、质量指标】。代价是【显存/编译时间/精度/维护成本】，在【边界条件】下没有收益。”

方括号必须用实际记录填写，没有测量的地方写“未测”。不要把教程假设写进简历作为个人成果。

## 可直接复制的报告结构

1. 问题与质量门槛：模型、输入、用途、允许误差。
2. 环境：硬件、系统、驱动、CUDA、PyTorch、后端版本、提交号。
3. 基线：启动命令、warm-up、测量次数、p50/p95、吞吐、峰值显存。
4. 证据：时间线截图或日志，说明为什么定位到这里。
5. 改动：只改变什么，为什么预期有效。
6. 结果：原始记录、数值/任务正确性、性能对照。
7. 局限：未测硬件、输入范围、负结果、潜在回退条件。

## 下一步项目的范围

优先完成一个可复现的小项目，而不是在 README 罗列十个框架。单卡视觉模型的 IO 优化、可恢复训练、一个小 kernel 的多尺寸验证、策略离线推理延迟分析，都可以成为可信起点。多卡和真实机器人经验应明确区分“阅读了解”“实际运行”“独立优化”。
