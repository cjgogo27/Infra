## 现场问题

PyTorch 模型运行正常，导出后却报不支持的算子；编译出的引擎换到另一台机器又不能直接加载。

> 带着问题读：ONNX 导出成功为什么不等于部署成功？

**模型导出（Export）、ONNX、TensorRT Engine、优化形状档（Optimization Profile）**

> **一句话听懂：部署编译把模型转换为目标硬件可执行的方案，必须同时验证形状、精度和兼容性。**

先区分三件事：保存参数只存数值；导出记录可执行计算与输入约束；编译根据目标硬件、精度和形状选择实现。ONNX 是交换表示，不保证任意 PyTorch 程序都能无损导出，也不保证导出后一定更快。

TensorRT 可优化支持的计算图并生成 engine。动态输入通常要定义可接受的形状范围和优化点；范围过大不保证各个形状都快，超出范围可能直接失败。数据依赖控制流、未支持算子或自定义操作要改写、分段执行或提供 Plugin，分别评估收益和维护成本。

TRT-LLM 面向大语言模型推理的专用能力，包含模型相关执行与服务组件；并不是把任何 VLA 丢进去就能整体优化。视觉编码器、语言骨干与动作头可能采用不同后端，跨后端传输也可能吃掉收益。

不要假定 engine 在任意 GPU、TensorRT 或 CUDA 环境都可移植。记录生成环境、目标架构、输入形状、精度、模型哈希，并按官方兼容规则判断。版本相关 CLI 容易变化，本书避免提供未经验证的跨版本万能命令。

**验证链：** PyTorch 基线 → 导出运行结果 → 编译结果 → 完整服务。每一步用同一输入集比较输出误差与任务指标，再做性能测量。随机张量覆盖 shape，真实样本覆盖分布。

**LabBot 落地：** 首先单独导出稳定形状的视觉编码器或动作头，验证颜色通道、归一化、动作顺序等接口，再接入闭环。
