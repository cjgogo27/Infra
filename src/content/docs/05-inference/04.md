## 现场问题

离线 benchmark 很快，在线请求却经常超时。模型执行只占几十毫秒，排队却超过一秒。

> 带着问题读：吞吐最高的 batch 为什么不一定最适合在线服务？

**连续批处理（Continuous Batching）、背压（Backpressure）、准入控制（Admission Control）**

> **一句话听懂：服务优化要控制等待中的工作量，防止 GPU 吞吐提升伴随用户排队失控。**

静态 batch 等整批完成；连续批处理允许完成的序列退出、新序列加入，缓解输出长度不齐的浪费。prefill 与 decode 的调度还会相互影响，分块 prefill 可在吞吐、首 token 和正在生成请求的间隔之间权衡。

系统接近饱和时，即使平均执行时间不变，队列也可能快速增长。不能靠无限队列吸收流量；要限制并发、待处理 token 或缓存预算，结合超时、取消和过载响应。已经取消的请求要及时释放资源。

健康检查只能证明进程或基础接口可用，模型实际可执行、剩余容量和加载状态还需额外观测。记录队列时长、执行时长、KV 使用量、失败率和客户端端到端延迟，才能把容量不足和内核慢区分开。

压测说明到达模型：固定并发的闭环客户端可能在慢下来后自动减少新请求，掩盖过载；按设定到达速率发送的测试更容易暴露排队，但需限制测试规模。两种方式都可用，不能混着比较。

**上下游影响：** GPU 调度策略影响产品 SLO，客户端重试又可能放大拥堵。重试应有预算并避免重复工作。

**LabBot 落地：** 过期相机观测不应该无限积压。保留最新可用观测、丢弃过期任务时，要由控制接口规定行为，不能把过时动作继续执行。
