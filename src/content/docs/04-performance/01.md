## 现场问题

有人建议重写 CUDA Kernel，有人建议换数据格式。两种都可能有用，但你还没有证据证明时间花在哪里。

> 带着问题读：为什么 profiler 表里所有 CUDA 时间相加可能大于墙钟时间？

**性能剖析（Profiling）、关键路径（Critical Path）、预热（Warm-up）**

> **一句话听懂：Profiler 把等待和执行摊在时间线上，让优化从猜测变成可验证的假设。**

先测不带 profiler 的稳定基线，再短时间采样分析。Profiler 本身会增加开销，特别是记录 shape、调用栈或完整内存信息时，不能直接把采样吞吐当生产结果。

PyTorch Profiler 适合把 Python/PyTorch 操作与设备内核对应；Nsight Systems 适合看 CPU、CUDA、流和通信时间线；Nsight Compute 用于深入少数热点内核的访存与执行指标。先看全局，再钻到内核，避免对不重要的热点做复杂优化。

CUDA 异步执行意味着 Python 返回时 GPU 可能仍在工作。用 CPU 墙钟测整体 batch，应在计时区间边界同步；测设备片段可用 CUDA Events。每个算子后都同步会破坏原本的并发，不能用这种测量结果推断生产重叠。

从时间线问四个问题：GPU 空洞前 CPU 在做什么；有无大量小 kernel；拷贝能否与计算重叠；通信尾部是否阻塞下一步。算子汇总表上的累计时间可能包含重叠，不能简单相加当作端到端时间。

**上下游影响：** 记录 shape 和输入长度，才能把性能变化与业务流量变化分开。

**LabBot 落地：** 为解码、归一化、编码器、动作头和指令发送分别标注范围；记录一次慢请求的全过程，再与普通请求对照。

跟着操作：[Profiler 判读实验](/Infra/labs/07-profiler/) 提供真实 CPU 采样摘要、打开 trace 的步骤和明确标注的 GPU 教学时间线。
