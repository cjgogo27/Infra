## 现场问题

模型在长序列上 OOM。你调用 empty_cache()，问题并未消失；开启 compile 后，第一次推理又特别慢。

> 带着问题读：empty_cache() 为什么不能释放仍被模型使用的权重？

**激活重算（Activation Checkpointing）、计算图（Graph）、图中断（Graph Break）、CUDA Graph**

> **一句话听懂：显存优化改变张量何时存在，编译优化改变一组操作如何执行。**

训练前向通常保留反向需要的激活。激活重算保存较少中间结果，反向时重新计算，换取更低峰值显存。不要与训练状态 checkpoint 混淆：一个是计算策略，一个是持久化恢复。重算区间里随机操作和可变状态也需要正确处理。

PyTorch 的 allocated 统计活跃 tensor 分配，reserved 包含缓存分配器管理的空间。empty_cache() 释放未使用缓存，不会释放仍被引用的活跃 tensor。排查泄漏先看是否把 loss tensor 或输出列表不断保留且携带计算图，再看形状变化与碎片。

torch.compile 尝试捕获和优化计算图；数据依赖的 Python 分支、频繁 shape 变化等可能造成图中断或重复编译。首次编译成本应与稳定执行分开报告，也要评估短任务能否摊销。CUDA Graph 主要减少重复提交的 CPU 开销，对内存地址、形状与控制流等有约束，不能和编译器视为同一个东西。

优化顺序可从小 microbatch、正确释放引用、混合精度、重算开始，接着评估状态分片或 offload。CPU offload 节省显存，但增加主机内存和传输压力。

**上下游影响：** 更少显存可能允许更大 batch，却也可能增加计算或传输，最终仍看有效吞吐与质量。

**LabBot 落地：** 将相机分辨率归入少量固定档位，可能减少动态形状触发的重编译；这会影响视觉信息，应同步评估任务成功率。
